# 密匣 MimaVault 安卓端对接规格说明

> 本文档依据 PC 端源码（`src\main\java\com\passwordmaster\`）整理，目标：安卓端与 PC 端 `.pmaster` 备份数据互通 **1:1 完全兼容**。
> 安卓端将复用同款加密算法（AES-256-GCM + PBKDF2WithHmacSHA256）与备份文件格式。

---

## 1. 数据目录与文件布局（PC 端）

| 项 | 值 | 说明 |
|---|---|---|
| 应用根目录 | `APP_DIR = user.dir`（jar 所在目录） | `AppConfig.APP_DIR` |
| 数据目录 | `APP_DIR\data\` | `AppConfig.DATA_DIR` |
| 数据库文件 | `APP_DIR\data\MimaVault.db` | SQLite，`jdbc:sqlite:` 直连 |
| 图片附件目录 | `APP_DIR\data\images\` | `AppConfig.IMAGE_DIR` |
| 配置文件 | `APP_DIR\data\config.json` | 目前仅预留 `dataDir` 字段 |
| 备份文件 | 任意路径，扩展名 `.pmaster`，默认命名 `MimaVault_backup_yyyyMMdd_HHmmss.pmaster` | 文件过滤器「密匣备份 (*.pmaster)」 |

> 安卓端注意：图片以**相对路径** `images/<文件名>` 记录在 `Entry.imagePath` 中，解析时以「数据目录 + 相对路径」为基准。

## 2. `.pmaster` 备份文件格式（最关键）

> **格式版本 v2（2026-08-30 起）**：新格式在密文前增加 header 显式携带密钥派生参数（盐 hex + 迭代次数），解决旧版"参数在加密内容内无法派生密钥"的循环依赖；旧格式（无 header 纯密文）仍受支持，向后兼容。

### 2.1 整体结构

```
.pmaster 文件（UTF-8 文本）
├── v2 新格式：MimaVault1$盐hex$迭代次数$Base64密文
│     └── header（明文，$ 分隔，共 4 段）：
│          MimaVault1 → 文件类型标识
│          盐hex     → PBKDF2 盐（16 字节 → hex 32 字符，小写）
│          迭代次数  → PBKDF2 迭代次数（如 600000）
│          Base64密文 → AES-256-GCM 密文 = Base64(iv(12B) + ciphertext)
│
└── v1 旧格式（无 header）：纯 Base64 密文
      └── AES-256-GCM 密文 = Base64(iv(12B) + ciphertext)
          └── 解密后为 JSON 文本（Gson pretty-printing 美化输出）
              └── BackupPackage 包
```

- 外层：整个备份包（JSON 明文）经 `AES-256-GCM` 加密后，**整体**再做一次 Base64 编码；新格式在其前拼接 header 写入文件；文件为 UTF-8 文本。
- header 中 `$` 为分隔符（共 4 段）；盐与迭代次数**明文存储**（不加密，仅用于派生密钥，不泄露密码本身）。
- 内层：`Base64(iv + ciphertext)` —— IV 12 字节直接拼接在密文前，一次性编码。
- 解密读取：`readString → trim → 判断 header → 解析参数派生密钥 → Base64 解码 → AES-GCM 解密 → JSON 解析`。
- 导出工具：`BackupUtil.export(entries, key, saltHex, iterations, path)`；导入工具：`BackupUtil.importBackup(path, masterPassword, currentKey)`。

### 2.2 JSON 包结构（BackupPackage）

| 字段 | JSON 类型 | 说明 |
|---|---|---|
| `version` | string | 固定 `"1"` |
| `exportedAt` | number | 导出时间，`System.currentTimeMillis()`（Unix 毫秒） |
| `items` | array | `BackupItem[]`，每条密码条目一项 |

### 2.3 条目字段（BackupItem）

| 字段 | JSON 类型 | 对应 Entry | 说明 |
|---|---|---|---|
| `category` | string | category | 分类：`"网站"` / `"应用"` / `"其他"`，缺省回填 `"网站"` |
| `platform` | string | platform | 平台名称（可空） |
| `account` | string | account | 账号（可空） |
| `password` | string \| null | passwordEnc | **带前缀的密文**：`"encrypted:" + Base64(iv+ciphertext)`；未设密码为 `null` |
| `phone` | string | phone | 手机号（可空） |
| `email` | string | email | 邮箱（可空） |
| `note` | string | note | 备注（可空） |
| `imageBase64` | string \| null | （图片附件） | 附件图片文件原始字节的标准 Base64（无换行），导出时若 `imagePath` 对应文件存在才写入 |
| `imageName` | string \| null | （图片附件） | 原图片文件名（含扩展名），如 `screenshot.png` |
| `gestureSeq` | string | gestureSeq | 手势密码数字序列文本，如 `"1,4,7,8,9"`（可空） |
| `syncStatus` | string | syncStatus | 同步状态，默认 `"local"`（为手机互联预留） |
| `createdAt` | string | createdAt | Gson 默认序列化 `java.util.Date` 的字符串（详见 §2.5 注意） |
| `updatedAt` | string | updatedAt | 同上 |

**密码字段关键约定**：
- 导出时**保持密文**，不写明文：`password = "encrypted:" + e.getPasswordEnc()`（`getPasswordEnc()` 为库内 AES-256-GCM 密文 `Base64(iv+ciphertext)`）。
- 导入还原时：`password` 以 `"encrypted:"` 开头则去掉前缀、保留密文写入 `password_enc`；安卓端可直接沿用该密文，也可用同一主密码派生密钥解密后重新入库。
- 内层条目密码密文由**主密码派生密钥**加密（同一把密钥也用于外层整包加密）。

### 2.4 加密流程

```
导出（v2）：
1. 读取全部条目（密码字段为库内密文，不解密）
2. 组装 BackupPackage JSON（密码加 "encrypted:" 前缀；图片文件读字节 → Base64）
3. JSON → AES-256-GCM 加密（密钥 = 当前会话主密码派生密钥，见 §3）
4. 密文 Base64 → 前拼接 header（MimaVault1$盐hex$迭代次数$）→ 写 UTF-8 文本 .pmaster
   （旧版 SHA-256 库无盐：不写 header，输出纯密文，保持 v1 兼容）

导入（v2，多通道依次尝试，任一成功即用）：
1. 读取文件 → trim
2. 通道①：以 "MimaVault1$" 开头 → 解析盐hex与迭代次数 → PBKDF2 派生密钥 → Base64 解码 → AES-GCM 解密
   （新格式标准通道，同库/跨库均可恢复，兼容未来库盐/迭代变化）
3. 通道②：无 header 或通道①失败 → 用当前库密钥（PasswordService.deriveKey：新库 PBKDF2 / 旧库 SHA-256）解密
   （救"当前版本导出的无 header 备份"）
4. 通道③：仍失败 → 用旧版 SHA-256 派生密钥解密（历史备份兜底）
5. 全部通道失败 → 报「主密码错误或文件损坏」
6. JSON 解析为 BackupPackage；items 为空或格式错误 → 报「备份文件格式不正确」
7. 恢复图片：imageBase64 → 解码 → 写入 data/images/<时间戳>_<原名>，imagePath 置为 "images/<新文件名>"
8. 按模式入库（覆盖 / 合并去重，见 §2.5）
```

### 2.5 导出 / 导入去重规则

- **覆盖模式**：`clearAll()` 清空现有 entries 后全量导入。
- **合并模式**：按 `keyOf = platform + "|" + account`（平台与账号均 null 视为空串）判断重复：
  - 与**现有库内条目**重复 → 跳过（`skipped++`）；
  - 备份包**内部**重复 → 仅第一条导入（`existingKeys` 集合随导入动态追加）；
  - 非重复 → 插入（`restored++`）。
- 导入完成提示：`成功 N 条，重复跳过 M 条`。

### 2.6 兼容性注意（已修复，安卓端需对齐多通道）

> 历史隐患（2026-08-30 前）：旧版 `MainFrame.onImport` 解密备份时硬编码旧版 SHA-256 密钥派生（`AesUtil.deriveKey`），而导出使用当前会话派生密钥（新库为 PBKDF2），导致新库备份导出后无法导入。
> **已修复**：导出侧在文件头携带 PBKDF2 盐/迭代参数（v2 header），导入侧按「① header PBKDF2 → ② 当前库密钥 → ③ 旧版 SHA-256」三通道依次尝试，新旧备份均可用同一份导入逻辑打开。
>
> **安卓端必须对齐**：
> - 导出 `.pmaster` 时：优先写 v2 header（`MimaVault1$盐hex$迭代次数$密文`），盐与迭代取当前库 `master_hash` 的 `pbkdf2$迭代$盐hex$哈希hex` 对应字段；若目标库为旧版 SHA-256（无盐），不写 header 输出纯密文。
> - 导入 `.pmaster` 时：按三通道依次尝试 —— ① 带 header 用 header 内参数 PBKDF2 派生；② 无 header 用当前库 `deriveKey`；③ 无 header 用 SHA-256 派生。任一成功即采用，全部失败才报「主密码错误或文件损坏」。

### 2.7 日期序列化注意

- `createdAt` / `updatedAt` 为 `java.util.Date`，由 Gson 默认 `DateTypeAdapter` 序列化（形如 `Aug 30, 2026 10:00:00 AM`，英文区域格式）。
- 安卓端解析建议：直接使用同款 Gson（保证 1:1），或实现兼容该格式的日期解析；写回时保持 Gson 默认格式以兼容 PC 端。
- PC 库内 `created_at` / `updated_at` 为 INTEGER（Unix 毫秒），导出时经 `java.util.Date` 转换。

## 3. 加密算法与参数

### 3.1 AES-256-GCM

| 参数 | 值 |
|---|---|
| 算法 | `AES` |
| 转换 | `AES/GCM/NoPadding` |
| 密钥长度 | 256 位 |
| IV | 12 字节（96 位），`SecureRandom` 随机，**每次加密新生成** |
| GCM 认证标签 | 128 位 |
| 明文编码 | UTF-8 |
| 密文格式 | `Base64( iv(12B) + ciphertext )` —— IV 前置拼接，整体 Base64（标准编码，无换行） |
| 完整性 | GCM 自带 AEAD 认证；解密失败抛 `IllegalStateException("解密失败，主密码可能不正确")` |

### 3.2 PBKDF2 密钥派生（新方案，标准）

| 参数 | 值 |
|---|---|
| 算法 | `PBKDF2WithHmacSHA256` |
| 盐 | 16 字节随机（`SecureRandom`） |
| 迭代次数 | **600000** |
| 输出 | **256 位（32 字节）** |
| 用途 | ① 派生 AES-256 密钥（条目加解密、备份包加解密）；② 生成主密码校验哈希 |

- `deriveKeyPbkdf2(char[] pwd, byte[] salt, int iterations)`：返回 `SecretKeySpec(derived, "AES")`。
- `pbkdf2Bytes(...)`：派生原始字节，用于哈希比较。

### 3.3 主密码哈希存储格式（settings.master_hash）

新格式（当前标准）：
```
pbkdf2$迭代次数$盐hex$哈希hex
示例：pbkdf2$600000$a1b2c3...32hex$d4e5f6...64hex
```
- 盐为 16 字节 → hex 32 字符；PBKDF2 输出 32 字节 → hex 64 字符；共 4 段以 `$` 分隔。
- 校验：解析迭代次数与盐 → PBKDF2 派生 → `MessageDigest.isEqual(expected, actual)` 常量时间比较。
- 生成：`AesUtil.buildPbkdf2Record(pwd, salt, 600000)`。

旧格式（兼容迁移）：
```
64 位小写 hex = SHA-256(主密码)
```
- 仅用于旧数据一次性迁移；登录校验通过后 `upgradeToPbkdf2` 用新密钥重加密全部条目并改写 `master_hash`。

### 3.4 旧版 SHA-256 密钥派生（兼容）

- `AesUtil.deriveKey(String pwd)`：`SecretKeySpec(SHA-256(pwd 的 UTF-8 字节), "AES")`。
- 仅旧库/旧备份兼容使用；`PasswordService.deriveKey` 会自动按存储格式选择（新格式走 PBKDF2，旧格式走 SHA-256）。
- 主密码全程以 `char[]` 承载，关键路径使用后立即 `Arrays.fill(..., '\0')` 清零（安卓端建议同样处理）。

## 4. 数据库 Schema（data\MimaVault.db）

### 4.1 settings 表

```sql
CREATE TABLE IF NOT EXISTS settings (
    id         INTEGER PRIMARY KEY CHECK (id = 1),
    master_hash TEXT NOT NULL,      -- pbkdf2$迭代$盐hex$哈希hex 或旧版 SHA-256 hex
    created_at INTEGER              -- Unix 毫秒
);
```
- 单行表（id 恒为 1）；`saveMasterHash` 使用 `ON CONFLICT(id) DO UPDATE` 覆盖写入。

### 4.2 entries 表

```sql
CREATE TABLE IF NOT EXISTS entries (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    category     TEXT DEFAULT '网站',   -- 网站 / 应用 / 其他
    platform     TEXT,                  -- 平台名称
    account      TEXT,                  -- 账号
    password_enc TEXT,                  -- AES-256-GCM 密文 Base64(iv+ciphertext)，可空
    phone        TEXT,                  -- 手机号
    email        TEXT,                  -- 邮箱
    note         TEXT,                  -- 备注
    image_path   TEXT,                  -- 附件图片相对路径，如 images/xxx.png
    gesture_seq  TEXT,                  -- 手势数字序列，如 1,4,7,8,9
    sync_status  TEXT DEFAULT 'local',  -- 同步状态（预留手机互联，未实现同步逻辑）
    created_at   INTEGER,               -- Unix 毫秒
    updated_at   INTEGER                -- Unix 毫秒
);

CREATE INDEX IF NOT EXISTS idx_entries_platform ON entries(platform);
CREATE INDEX IF NOT EXISTS idx_entries_category  ON entries(category);
```

### 4.3 字段类型与含义对照

| DB 列 | 类型 | 含义 | 是否参与备份 |
|---|---|---|---|
| id | INTEGER PK | 自增主键 | ❌（备份不含 id，导入重新分配） |
| category | TEXT | 分类 | ✅ |
| platform | TEXT | 平台 | ✅ |
| account | TEXT | 账号 | ✅ |
| password_enc | TEXT | 密码密文 | ✅（导出带 `encrypted:` 前缀） |
| phone | TEXT | 手机号 | ✅ |
| email | TEXT | 邮箱 | ✅ |
| note | TEXT | 备注 | ✅ |
| image_path | TEXT | 图片相对路径 | ✅（转为 imageBase64/imageName） |
| gesture_seq | TEXT | 手势序列 | ✅ |
| sync_status | TEXT | 同步状态 | ✅（默认 local） |
| created_at | INTEGER | 创建时间(ms) | ✅（转 Date） |
| updated_at | INTEGER | 更新时间(ms) | ✅（转 Date） |

- 兼容升级：初始化时 `PRAGMA table_info` 检测缺失列（`category`、`sync_status`）并 `ALTER TABLE ... ADD COLUMN` 补齐。
- 安卓端建库可直接复用上述 SQL；建议保留 `sync_status` 列并默认 `local`。

## 5. 图片附件

- **存储方式**：独立文件，存放于 `data\images\`；**不入库、不入备份 JSON 明文**（备份内为 Base64 文本）。
- **引用方式**：`Entry.imagePath` 存相对路径 `images/<文件名>`（如 `images/1699999999999_screenshot.png`），解析基准为数据目录。
- **命名规则**：导入/新增时统一 `System.currentTimeMillis() + "_" + 原文件名`，避免冲突；扩展名白名单：`.jpg .jpeg .png .gif .bmp .webp`。
- **备份导出**：按 `imagePath` 找到文件 → 读原始字节 → 标准 Base64 → `imageBase64`；同时写 `imageName`（原文件名，含扩展名）。
- **备份导入**：`imageBase64` 解码 → 写 `data/images/<时间戳>_<imageName>` → 覆盖 `imagePath = "images/<新文件名>"`。
- 若 `imageBase64` 为空/文件不存在 → 条目仍导入但无图片。

## 6. 手势密码

- **存储格式**：数字序列文本，逗号分隔，如 `"1,4,7,8,9"`；可为 null（未设置）。
- **九宫格编号规则**（`GesturePanel`，3×3，编号 = `row * 3 + col + 1`，左上 → 右下）：

```
1  2  3
4  5  6
7  8  9
```

- 录入：`GestureDialog` 支持九宫格连线（自动记录点号序列）或手动输入 `1-9` 数字（可逗号分隔）。
- 解析：`setSequence` 按 `[,，\s]+` 分割，仅接受 `1~9` 数字；显示时按序列绘制轨迹线。
- 序列**不存储重复点**（录入时 `!sequence.contains(num)` 才追加）。
- 安卓端注意：手势仅作为**条目附加信息**，不是应用解锁密码；`gestureSeq` 明文存储（非加密）。

## 7. 主密码验证流程（登录）

```
用户输入主密码（char[]）
  → PasswordService.verifyMasterPassword(char[])
      → 读取 settings.master_hash
      → 以 "pbkdf2$" 开头？
          ├─ 是（新格式）：split('$') 取 4 段 → 解析迭代次数(parts[1])、盐hex(parts[2])、期望哈希(parts[3])
          │      PBKDF2WithHmacSHA256(密码, 盐, 迭代) 输出 256 位 → MessageDigest.isEqual 比较
          │      → 通过 = MATCH；失败 = MISMATCH
          └─ 否（旧格式，64hex）：sha256Hex(密码) equalsIgnoreCase 比较
                 → 通过 = MATCH_NEED_UPGRADE（提示并执行一次性迁移 upgradeToPbkdf2）
                 → 失败 = MISMATCH
```

- **迁移流程**（旧→新）：旧密钥逐条解密预检全部条目（任一失败即中止、数据不改动）→ 逐条用 PBKDF2 新密钥重加密写回 → 最后改写 `master_hash` 为新格式。
- **登录后密钥派生**：`PasswordService.deriveKey(char[])` 按 `master_hash` 格式自动选择（新格式 PBKDF2：盐+迭代从记录解析；旧格式 SHA-256），派生密钥用于条目密码加解密与备份导出。

## 8. 安卓端对接要点（1:1 兼容清单）

1. **加密库兼容**：Android 内置 JCA 支持 `PBKDF2WithHmacSHA256`（`SecretKeyFactory`）与 `AES/GCM/NoPadding`（API 21+，GCM 认证标签用 `GCMParameterSpec`）。无需额外 BouncyCastle。
2. **密钥派生**：严格复刻 `PBKDF2WithHmacSHA256`，盐 16B、迭代 600000、输出 256 位；备份解密按三通道实现（① header 内参数 PBKDF2 → ② 当前库密钥 → ③ SHA-256 兜底，见 §2.6）；导出写 v2 header（`MimaVault1$盐hex$迭代次数$密文`）。
3. **主密码哈希**：生成与校验格式 `pbkdf2$迭代$盐hex$哈希hex`；校验用常量时间比较。
4. **密文格式**：条目密码与备份包均为 `Base64(iv(12B)+ciphertext)`，IV 每次随机；GCM Tag 128 位。
5. **备份 JSON**：用同款 Gson 或严格兼容字段名/结构；`password` 前缀 `encrypted:` 规则、`version="1"`、`exportedAt` 毫秒、日期格式按 §2.7。
6. **去重规则**：合并导入按 `platform + "|" + account` 判重，重复跳过；覆盖模式清空后导入。
